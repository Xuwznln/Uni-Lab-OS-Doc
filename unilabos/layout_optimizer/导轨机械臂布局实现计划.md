## 0. 前置判断与公共基础设施

### 0.1 范式判断（决定整体架构）

现有 skill `lab-layout-optimizer` 的内核是**差分进化（DE）随机搜索**：意图 → 约束 → `/optimize/auto` 多起点 DE → 推前端。它解决的是"约束满足下的随机寻优"。

导轨机械臂逻辑是**确定性解析布局**：参数定死后坐标唯一、算出来即可，不需要搜索。

**架构决策：** 做成一个**新的兄弟 skill（`rail-layout`）**，核心算法写成纯函数模块 `rail_layout.py`，通过给 `server.py` 增加 2~3 个确定性端点暴露给 agent，**复用现有服务的 I/O 端点，但不复用 `/optimize` 优化内核**。

### 0.2 可复用的原技能能力（贯穿三个阶段）


| 能力                       | 来源                                        | 用途                                                     |
| ------------------------ | ----------------------------------------- | ------------------------------------------------------ |
| `GET /devices`           | `server.py:295`                           | 拿设备 bbox、`openings`(朝向)、footprint                      |
| `GET /scene/lab`         | `server.py:891`                           | 读房间尺寸 width/depth                                      |
| `POST /scene/placements` | `server.py:914`                           | 推坐标到前端（文档所说"原 skill 的 curl 方法"），**需发两次做 version bump** |
| `LabSpec.obstacles` 字段   | `server.py:486`                           | 阶段三与环境障碍物的碰撞检测输入                                       |
| 面积/边界冲突预检逻辑              | `feasibility.py:84-114`                   | 阶段一面积可行性可直接借用判据写法                                      |
| 结构化冲突 + 放宽建议范式           | `feasibility.py:Conflict` + SKILL.md 失败分支 | 三个阶段统一的"不可行 → AskQuestion 放宽"交互                        |
| 前端按 placement 自动建设备      | `lab3d.html` / README §11.2               | 空场景直接推坐标即可渲染，无需先手动加设备                                  |


### 0.3 公共前置交付物（三阶段共享，需先做）

1. **机械臂型号表** `rail_arm_models.json`（新建，仿 `footprints.json`）—— **本计划暂不做，优先级后推**
  - 键：机械臂型号 id；值：`{rail_length L, working_radius, bbox[w,h]}`
  - 现阶段处理：**工作半径统一取默认值 `working_radius = 0.3m`**（导轨长度 L、bbox 暂从 `/devices` 的 bbox 推或用占位值），不引入型号表。
  - 理由：可行性检查的 `L`、工作半径、可达性判定最终都依赖它，但为先跑通主流程暂用默认值。
  - **后续待补（TODO）**：正式实现时必须补上 `rail_arm_models.json`，把工作半径/导轨长度/bbox 改为按机械臂型号查表，替换掉这里的 0.3m 默认值。
2. **默认距离参数** `DEFAULT_PARAMS`（`rail_layout.py` 内集中定义，允许用户覆盖）
  - `a=0.5, b=0.2, c=0.3, d=0.3, e=0.2`（米；具体值可调）
  - 硬约束：默认 `b < 工作半径`、`e < 工作半径`（见逻辑文档可达性约定）。
3. **核心纯函数模块** `rail_layout.py`（无副作用导入，便于多进程/单测，仿 `feasibility.py`）
4. **服务端点**（加到 `server.py`）：`POST /rail/feasibility`、`POST /rail/layout`（可选 `POST /rail/validate`）
5. **新 skill** `rail-layout/SKILL.md`：负责高层编排（拉数据 → 调端点 → 不可行 AskQuestion → 推前端）

## 阶段一：可行性检查

对应工作流文档"可行性检查"。目标：判断布局是否可行，同时确定需要多少台机械臂和堆栈。

### 交付产物

- **纯函数** `check_feasibility(devices, ordered_instruments, lab, arm_model, params) -> FeasibilityReport`
  - 单一函数内部依次跑全部子判据（不拆成多个微脚本，因子判据共享 `sum_W / L_max / L_2nd / 参数` 等中间量）。
  - 子判据：
    1. **面积检查**：仪器+机械臂+堆栈总面积 ≤ 房间面积（借用 `feasibility.py:84` 写法）
    2. **算台数**：`n_arm = ceil(sum_W / (2L))`，`n_stack = n_arm - 1`（**粗估**，多退少补在阶段三处理）
    3. **短边不等式 1/2**（见逻辑文档 3.2）
    4. **长边不等式**：`2a + n·L + (n-1)(2e+h_s) ≤ 房间长边`，并反解长边几何上限 `n_max`
    5. **可达性**：`b < 工作半径` 且 `e < 工作半径`（参数级廉价校验）
  - 返回结构：`{feasible: bool, n_arm, n_stack, n_max, mode_hint, reasons: [...], suggestions: [...]}`
- **服务端点** `POST /rail/feasibility`：包装上面的函数，返回上述 JSON。
- **工作半径默认值** `working_radius = 0.3m`（本计划暂用，型号表 `rail_arm_models.json` 后推，见 0.3 的 TODO）。

### 可复用原技能的部分

- `GET /devices` 取 bbox/朝向；`GET /scene/lab` 取房间尺寸。
- `feasibility.py` 的面积/单设备超尺寸判据写法与 `Conflict(kind, message, suggestion)` 数据结构。
- SKILL.md 中"不可行 → AskQuestion 让用户放宽"的交互范式（扩大房间/减仪器/换更短导轨/改参数）。

### 测试（`tests/test_rail_feasibility.py`）

- 面积恰好可行 / 面积超限 → feasible 翻转正确。
- 台数公式边界：`sum_W` 恰好等于 `2nL`、刚超过 `2(n-1)L` → `n_arm` 取值正确。
- 长边不等式：构造刚好放下 n 台、放不下 n 台的房间 → `n_max` 与 feasible 正确。
- 短边不等式 1 成立/不成立、不等式 2 不成立（判不可行）三种分支。
- 可达性：`b ≥ 工作半径` 或 `e ≥ 工作半径` → 报对应 reason。
- 报告字段完整性：不可行时 `reasons` 与 `suggestions` 一一对应、非空。

## 阶段二：布局机械臂和堆栈

对应工作流文档"布局机械臂和堆栈"。目标：算出全部机械臂与堆栈的坐标。

### 交付产物

- **纯函数（第一台与剩余合并为一个）** `place_arms_and_stacks(lab, n_arm, arm_model, params, mode="near_wall") -> {arms, stacks}`
  - `mode`：`near_wall`（默认，靠墙）/ `centered`（居中，仅用户显式要求且满足短边不等式 1）。
  - 后续机械臂沿长边按固定间距 `L + 2e + h_s` 偏移；堆栈中轴线对齐臂中轴线、夹在相邻臂之间、距臂 `e`。
  - **每台机械臂必须输出四个角坐标**（左下/右上等），供阶段三反推仪器坐标。
  - 返回：`arms = [{id, center, theta, corners:[4]}], stacks = [{center, bbox}]`。
- **距离参数默认值** `DEFAULT_PARAMS`（公共前置，本阶段落地为可覆盖入参）。
- **服务端点** `POST /rail/layout` 的机械臂/堆栈部分（与阶段三共用同一端点，见下）。

### 可复用原技能的部分

- 坐标系约定、`PositionXYZ/rotation(theta)` 输出格式（`server.py:511` 的 `PlacementResult`），保证与 `POST /scene/placements` 兼容。
- 机械臂/堆栈作为设备从 `/devices` 取 bbox。

### 设计要点（已据问答确定）

- 第一台与剩余**合并为一个函数**：后续臂/堆栈是纯几何偏移，唯一分支是第一台的 `mode`，作入参即可，无需在两脚本间传中间状态。
- 距离参数**必须有默认值**，集中管理、允许覆盖。

### 测试（`tests/test_rail_arms.py`）

- 靠墙模式：臂长边到墙距离 = `d + b + L_max`，校验第一台坐标。
- 居中模式：臂 bbox 中轴线与房间中轴线重合，短侧到墙仍为 `a`。
- 多臂偏移：n=2/3 时相邻臂中心间距 = `L + 2e + h_s`，堆栈数 = n-1、居中夹层。
- 四角坐标输出正确（与中心+bbox+theta 自洽）。
- 越界检查：臂+堆栈沿长边总长 ≤ 房间长边（与阶段一 `n_max` 一致）。

## 阶段三：按实验步骤顺序布置各仪器

对应工作流文档"按实验步骤顺序布置各仪器"。目标：把全部仪器按流程排到机械臂周围并算出坐标+朝向。

### 交付产物

- **纯函数（"选侧 + 选仪器 + 算坐标"合并）**
`assign_and_place_instruments(arms, ordered_instruments, params) -> placements[]`
  - 内部完成：
    1. **确定性的"哪台臂哪一侧"顺序**（从下到上、从左到右、左先右后）—— 不交给 agent。
    2. **贪心装箱填满单侧**：`cost_w(i)=sum_W_i+(i-1)c ≤ L`。
    3. **用四角反推坐标**：左侧用左下角、右侧用右上角；同侧内边缘统一距臂 `b`。
    4. **朝向 theta**：据 `/devices` 的 `openings` 算每台仪器旋转角，使其面向导轨（左侧朝 +x、右侧朝 −x）。
    5. **多退少补**：删除周围无仪器的空臂；末尾仍有剩余仪器则 `n_arm+1` 回阶段二重排（见反馈环）。
  - 输出含 `position + rotation(theta)`，可直接喂 `POST /scene/placements`。
- **校验函数（碰撞降级为守卫）** `validate_placements(placements, lab, obstacles, arms) -> conflicts[]`
  - 仪器 AABB vs 环境障碍物（`obstacles`）；仪器越墙/越工作半径的后置断言。
  - **不做**仪器之间/仪器与臂的搜索式避碰（构造上已不碰）。
- **服务端点** `POST /rail/layout`：串联阶段二+阶段三，返回完整 placements；可选 `POST /rail/validate`。

### 可复用原技能的部分

- `POST /scene/placements` 推坐标（**发两次** version bump）—— 即工作流文档所说"原 skill 的 curl 方法"。
- `LabSpec.obstacles` 作为障碍物输入做环境碰撞检测。
- 前端自动建设备能力：空场景直接推即可渲染。
- `openings` 朝向字段（`/devices` 返回）用于算 theta。

### 设计要点（已据问答确定）

- **碰撞检测有必要但降级**：构造上仪器互不碰，碰撞检测只用于①与环境障碍物②越界/越工作半径断言。
- **"哪台臂哪一侧"不交给 agent**：线性流程下完全确定，交 LLM 会引入不确定性。
- **agent 职责收敛为高层编排**：拉数据 → 可行性 → 调布局 → （可选）校验 → 推前端。
- **多退少补的反馈环**：删/补臂会改几何 → 仪器坐标要重算，故阶段二/三由同一上层 routine 串起来，不让 agent 中途手动判断。
- **朝向必须算**：否则前端摆出朝向全错。

### 测试（`tests/test_rail_instruments.py`）

- 单侧装箱：`cost_w` 边界（恰好填满 / 多一台溢出）→ 选中仪器集合正确。
- 坐标反推：左侧仪器右边缘对齐 `arm_left - b`、自下而上；右侧左边缘对齐 `arm_right + b`、自上而下。
- 朝向：左/右侧仪器 theta 使 `openings` 指向导轨。
- 多退少补：构造"留空臂"场景验证删臂；构造"末尾仍有剩余"场景验证补臂+重排。
- 端到端：11 台线性流程 + 2 臂 → placements 数=11、无越界、流程顺序连续（可对照之前的 demo 图）。
- 环境碰撞：放一个 obstacle 与某仪器重叠 → `validate_placements` 报冲突。

## 交付顺序与里程碑

1. **M0 公共前置**：`rail_layout.py` 骨架 + `DEFAULT_PARAMS` + 工作半径默认 0.3m（`rail_arm_models.json` 后推，见 0.3 TODO）。
2. **M1 阶段一**：`check_feasibility` + `/rail/feasibility` + 单测。
3. **M2 阶段二**：`place_arms_and_stacks` + 单测。
4. **M3 阶段三**：`assign_and_place_instruments` + `validate_placements` + `/rail/layout` + 单测。
5. **M4 skill 编排**：`rail-layout/SKILL.md` 串联端点 + 不可行 AskQuestion + 推前端，端到端跑通可视化。

## 与现有优化器的边界（避免混淆）

- **不复用** `/optimize`、`/optimize/auto`、DE 相关 seeder/约束求解。
- **复用** `/devices`、`/scene/lab`、`/scene/placements`、`obstacles`、面积预检判据、AskQuestion 失败交互范式。
- 两套 skill 并存：随机寻优场景走 `lab-layout-optimizer`，导轨线性流程走 `rail-layout`。
