# 设备模板库与类别选择

:::{admonition} 阅读角色
- **业务负责人**：确认设备用途、动作名称、参数单位、成功标准和安全边界。
- **开发人员**：实现设备合同、连接方式、启动图节点、模拟能力和测试。
- **验收人员**：验证参数越界、断线、超时、联锁、未知结果和真机恢复。
:::

设备模板库可以理解为一份“常见设备能力清单”。它按设备用途和可执行操作分类，帮助项目先统一业务名称，再接入具体品牌和型号。用户只需选择与现场设备能力匹配的类别，不需要接入模板库中的全部类别。

模板类别和数量会随 Uni-Lab OS 版本及用户设备包发生变化。接入时请以当前设备包检查报告和 Uni-Lab OS 实际识别出的设备类别、动作与状态为准，不使用固定数量判断模板是否完整。

设备仓库模板地址：[Uni-Lab-package_management（instrument-category-hierarchy 分支）](https://github.com/dijkstra402/Uni-Lab-package_management/tree/feat/instrument-category-hierarchy)

## 第一次接入时如何选模板

按下面顺序描述设备，比直接搜索厂商型号更容易找到可复用模板：

1. **用途**：设备是移液、温控、读板、存储、搬运，还是检测？
2. **对象**：它处理液体、微孔板、吸头、瓶子，还是其他物料？
3. **动作**：需要“设置/启动/停止/读取/装载/取出”中的哪些动作？
4. **接口**：设备通过 PLC、串口、网络 API 还是桌面软件连接？
5. **安全条件**：有哪些门禁、急停、温度上限或人工确认要求？

| 业务描述 | 可先查看的类别示例 | 需要进一步确认 |
| --- | --- | --- |
| 按体积吸液和分液 | 液体处理设备 | 通道数、吸头和容器兼容性 |
| 控温并振荡微孔板 | 加热/振荡设备 | 温度范围、转速和板位锁定 |
| 读取板的光学信号 | 读板设备 | 检测方式、协议和结果文件 |
| 在多个位置存取微孔板 | 存储设备（培养箱、板酒店、旋转堆栈） | 同时登记 Stack/Site 物料树和旋转/光电设备能力，见[光电堆栈与旋转堆栈：物料 + 设备](stack.md) |
| 控制一组气缸、阀和传感器 | PLC 工站 | 点位表、握手和联锁 |

表中的类别只是选择方向，不代表指定分支的完整清单。找不到完全匹配时，先选语义最
接近的类别，并记录缺少的动作，避免在工作流里调用私有方法。

## 当前代码已经覆盖的主要设备方向

Uni-Lab OS 支持以下主要设备方向。这表示系统具备相应的接入结构，不代表所有品牌型号都已完成真机验证。接入新设备时，仍要以本地设备包检查报告和现场验收结果为准。

| 业务方向 | 包含的设备示例 |
| --- | --- |
| 液体与反应处理 | 液体处理工作站、泵和阀、粉体加料、加热搅拌、旋转蒸发、真空设备 |
| 分析检测 | HPLC、GCMS、NMR、拉曼、紫外、XRD、读板机、天平 |
| 搬运与执行 | 机械臂、AGV、夹爪、电机、CNC、分离和封口设备 |
| 存储与培养 | 自动仓储/培养设备、资源容器和组合工作站 |
| 电池实验 | 电池测试系统和扣式电池装配相关设备 |
| 系统验证 | 虚拟设备和模拟工作台 |

业务人员先选择最接近的方向，再由开发人员检查同类实现的动作名称、参数和状态。不能仅凭“代码中有这个目录”就判断某个具体型号已经可用。

## 一个合格模板应该说明什么

| 内容 | 业务解释 | 验收问题 |
| --- | --- | --- |
| 设备 ID | 系统识别设备的稳定身份证 | 更换中文名称后，历史流程是否仍能找到它？ |
| 显示名称/描述 | 页面上给操作者看的名称和用途 | 不看代码能否知道它做什么？ |
| 动作说明 | 每个动作的输入、输出、单位和失败条件 | 操作者能否按表单填写？ |
| 状态 | 连接、忙、就绪、报警等只读信息 | 运行中能否判断下一步？ |
| 连接配置 | PLC 地址、端口、API 地址等 | 是否与凭证分开保存？ |
| 模拟实现 | 不连接真机的验证路径 | 能否先验证工作流？ |

## 设备包的最小目录

```text
my-device-package/
├── pyproject.toml                  # Python 包与依赖
├── package.yaml                    # 包身份和工作流清单
├── README.md                       # 使用说明、版本和限制
├── devices/                        # 设备类与动作
├── registry/devices/               # 需要 YAML 注册时的目录
├── resources/                      # 设备/物料模型（如有）
├── workflows/                      # 可复用操作和完整流程
├── tests/                          # 动作规范、模拟和启动清单检查
└── .github/workflows/              # 自动检查（可选）
```

设备类别、动作和实现应保持一一对应：设备 ID 不能重复，工作流不能依赖没有登记的
方法。模板仓库中的适配器通常把 Uni-Lab 装饰器放在设备类旁边，同时将底层驱动作为
内部实现，这样换通信方式时不会改变业务工作流。

## 把业务操作登记成系统动作

```python
from unilabos.registry.decorators import action, device, topic_config


@device(
    id="example_reader",
    category=["plate_reader"],
    displayname="示例读板机",
    description="读取微孔板信号",
)
class ExampleReader:
    @property
    @topic_config(period=5.0)
    def status(self) -> str:
        return "ready"

    @action(displayname="读取板信号", description="按协议读取一次板信号")
    def read_plate(self, plate_barcode: str) -> dict:
        return {"success": True, "plate_barcode": plate_barcode, "result_uri": "..."}
```

- `@device` 标记设备身份、分类和说明；
- `@action` 标记可被工作流调用的业务动作；
- `@topic_config` 标记需要定期对外发布的只读状态；
- 参数类型注解和 `Args:` 文档会帮助系统生成页面表单；
- 内部辅助方法以下划线开头，或用 `@not_action` 明确不作为动作公开。

### 动作参数规范

| 规则 | 正确示例 | 错误示例 |
| --- | --- | --- |
| 名称表达业务含义 | `temperature_c` | `p1`、`register_4001` |
| 类型明确 | `float`、`int`、`bool`、`str` | 无注解、`Any` |
| 单位唯一 | 参数名/描述明确 `c`、`rpm`、`ml` | 同一参数同时接受 °C/°F |
| 范围可校验 | `0 <= speed_rpm <= 300` | “正常范围” |
| 枚举有限 | `mode in {'heat', 'cool'}` | 任意字符串透传设备 |
| 默认值安全 | 查询参数或停止值 | 默认启动加热/运动 |
| 返回结构稳定 | `success/message/value` | 有时 `bool`、有时字符串 |

参数校验放在驱动边界，协议转换之前执行。错误输入使用 `ValueError`；通信失败、超时和设备拒绝使用可区分的异常，不要统一返回 `False`。

每个需要出现在页面和工作流中的操作都应明确使用 `@action` 登记。不要依赖系统自动猜测哪些程序方法属于业务动作，否则升级后动作名称可能发生变化。

## 怎样检查模板是否可用

开发人员完成模板后，可在包根目录执行：

```bash
python -m compileall my_device_package
unilab package inspect --path . --out ./inspect-output
```

结果中重点看：

- 设备 ID 和类别是否出现在目录；
- 动作参数是否有正确类型和描述；
- 构造函数是否没有自动连接硬件；
- `package.yaml` 引用的文件是否全部存在；
- 模拟启动图（Graph JSON）是否能完成一次成功和一次失败路径。

## 成功后业务人员会看到什么

- 目录中能按类别找到设备，中文名称和用途清楚；
- 动作表单只显示允许填写的字段，并注明单位和范围；
- 工作流画布可以拖入已登记动作，而不需要记忆厂商命令；
- 设备状态和错误提示能帮助判断是参数问题、通信问题还是设备报警；
- 新型号可以复用同一类别的动作规范，不必重写已有工作流。

## 常见问题

| 问题 | 原因 | 建议 |
| --- | --- | --- |
| 找不到对应类别 | 当前 Catalog 没有完全匹配项 | 选择最接近类别并记录缺口，不自行杜撰类别 |
| 一个型号出现两次 | ID 在 AST 和 YAML 中重复登记 | 保留一个明确的注册所有者 |
| 动作名称太技术化 | 直接暴露厂商函数名 | 映射为“启动/停止/读取”等业务名称 |
| 模板通过检查但不能运行 | 只验证了导入，未验证连接和状态 | 增加模拟 启动图 和真实联调验收 |
| 模板数量与其他环境不一致 | Uni-Lab OS 版本或用户设备包不同 | 以当前设备包检查报告和运行环境实际识别结果为准 |

## 上线前检查清单

- [ ] 已按用途、物料和动作选择类别，而不是只按厂商名称选择；
- [ ] 设备 ID 唯一稳定，显示名称和 ID 分离；
- [ ] 每个动作有业务名称、参数、单位、结果和错误说明；
- [ ] 状态、连接和安全停止动作已登记；
- [ ] 模拟路径与真实路径的动作名称和参数保持一致；
- [ ] `package.yaml`、注册文件和 Python 类的身份一致；
- [ ] 已运行 Python 编译和包检查，并保留结果；
- [ ] 模板缺口和未验证能力已在 README 中标注。

设备接入的具体实现见[设备接入模板总览](device-template.md)；如果需要先定义设备
动作而尚未确定通信方式，可从[通用设备规范](generic-device.md)开始。
