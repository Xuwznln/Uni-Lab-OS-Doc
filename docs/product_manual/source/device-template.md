# 1. 设备接入模板

:::{admonition} 阅读角色
- **业务负责人**：确认设备用途、动作名称、参数单位、成功标准和安全边界。
- **开发人员**：实现设备合同、连接方式、启动图节点、模拟能力和测试。
- **验收人员**：验证参数越界、断线、超时、联锁、未知结果和真机恢复。
:::

这组模板写给第一次接触 Uni-Lab OS 的业务人员、项目实施人员和设备开发人员。按照本章操作后，一台真实设备应能出现在系统设备清单中，页面能显示它的状态，工作流也能调用它的动作。

文档中所说的“设备接入”，可以简单理解为：先告诉系统“这是什么设备、能做什么”，再补充“系统通过什么方式控制它”。前一部分要保持稳定，后一部分可以根据 PLC、串口或厂商软件分别实现。这样将来更换设备品牌时，原有业务流程不需要全部重写。

:::{note} 本章中的几个词
**设备类型**表示一类设备，例如“蠕动泵”；**设备实例**表示现场的一台具体设备，例如“一号蠕动泵”；**动作**表示操作员希望设备完成的事情，例如“设置转速”；**启动图（Graph JSON）** 是系统启动时读取的设备和物料清单；**Catalog** 是系统从设备包中识别出的可用类型清单。
:::

## 先判断设备由什么方式控制

| 设备现状 | 优先阅读 | 典型设备 |
| --- | --- | --- |
| 设备有 PLC 和状态点位 | PLC 控制的工站 | 传送、抓取、液体处理工站 |
| 设备提供串口、TCP 或 Modbus 协议 | 串口／网络连接 | 泵、阀、温控器、网关 |
| 设备只能由厂商软件控制 | 上位机 API 接入；没有 API 时再看鼠标模拟 | 分析仪、读板机、封闭软件 |
| 设备会旋转、选层或用光电判断占位 | [光电堆栈与旋转堆栈：物料 + 设备](stack.md) | 旋转仓、带光电的料架；同时登记 Stack/Site 物料树和设备能力 |
| 需要先统一设备的动作名称和参数 | 通用设备规范 | 加热器、振荡器、泵、测试设备 |

## 从资料准备到现场可用

无论设备使用哪种协议，都按同一顺序完成：

1. **收集设备资料**：型号、固件、协议、动作、参数、单位、范围、返回值、错误码和安全条件；
2. **列出系统要提供的能力**：用 `@device` 登记设备，用 `@action` 登记可执行操作，用 `@topic_config` 登记页面需要显示的只读状态；
3. **实现控制方式**：把 PLC、串口、TCP、HTTP/SDK 或鼠标操作写在设备驱动内部，不暴露给业务流程；
4. **让系统发现设备**：在 `devices/__init__.py` 中导入设备模块，避免代码已经写好但系统清单中找不到；
5. **加入启动清单**：在 启动图 中填写现场设备的唯一编号、设备类型和连接参数；
6. **先做离线检查**：检查代码和设备包结构，再使用模拟设备进行试运行；
7. **现场验收**：最后验证真机、联锁、超时、断线和恢复。

完成接入至少要交付：设备 Python 模块、启动图 节点、模拟或测试替身、参数/错误说明和自动化测试。

## 每个字段应该怎样填写

| 项目 | 必须遵守的规则 | 示例 |
| --- | --- | --- |
| `@device.id` | 设备类型的永久编号。全局唯一、稳定、使用小写英文和下划线；不使用中文、空格、IP 或序列号 | `my_lab_pump` |
| 启动图 `id` | 现场这台设备的编号。同型号有多台设备时，每台都要不同 | `pump_01` |
| `category` | 按工艺能力分类，不按厂商营销名称分类 | `['liquid_handling', 'pump']` |
| 动作名 | 使用业务动词，`snake_case`；不暴露 HTTP 路径、寄存器或按钮坐标 | `set_speed` |
| 参数名 | 表达业务含义并保持跨驱动一致 | `speed_rpm` |
| 参数类型 | 必须有 Python 类型注解；避免无约束 `Any` | `float` |
| 单位 | 写入参数名或描述，且只允许一种单位 | `temperature_c` |
| 范围 | 在驱动入口校验；越界立即抛 `ValueError` | `0 <= speed_rpm <= 300` |
| 默认值 | 只使用安全、无歧义默认值；危险动作参数不应靠默认值启动 | `speed_rpm=0.0` |
| 返回结果 | 使用固定结构，至少能判断成功或失败；不能同一个动作有时返回文字、有时返回数字 | `{'success': True, 'message': '...'}` |
| 页面状态 | 读取状态不能让设备产生动作；要能表示待机、运行、故障和无法确认 | `idle/running/fault/unknown` |
| 密码或令牌 | 不写在代码和 启动图 中，通过环境变量或系统密钥功能提供 | `token_env='PUMP_TOKEN'` |

动作说明至少写清：用途、参数单位和范围、成功判据、超时语义、是否可取消、是否允许安全重试。

## 把现场设备加入启动清单

```json
{
  "id": "pump_01",
  "name": "一号蠕动泵",
  "children": [],
  "parent": null,
  "type": "device",
  "class": "community.my_device_package.my_lab_pump",
  "position": {"x": 0.0, "y": 0.0, "z": 0.0},
  "config": {
    "port": "/dev/tty.usbserial-0001",
    "baudrate": 9600,
    "timeout": 2.0,
    "auto_connect": false
  },
  "data": {"status": "offline"}
}
```

- `class` 表示使用哪一种设备模板，必须从设备包检查报告中复制完整类型名称，例如 `community.my_device_package.my_lab_pump`；不要凭文件路径猜写；
- `config` 保存这台设备的连接设置，字段名称必须与设备代码接收的参数名称一致；
- `data` 保存页面首次显示的状态，不能用于保存密码；
- `position` 只决定页面中的布局位置，不代表机器人可以直接使用的运动坐标；
- 新接入阶段保持 `auto_connect: false`，先显式连接和验证身份。

## 交付前检查

```bash
python -m compileall my_device_package
unilab package inspect --path . --out ./inspect-output
```

第一条命令检查代码是否能正常加载；第二条命令生成设备包检查报告。报告必须满足：设备编号没有重复、动作表单中的字段正确、启动图 能找到对应设备类型、仅仅启动系统不会让设备自动运动，以及错误配置会给出明确提示。

## 接入完成的判定

- Uni-Lab OS 页面中能看到设备实例、状态和可用动作；
- 每个动作的输入字段有中文说明、单位和取值范围；
- 成功、失败、超时和人工介入状态有明确提示；
- 设备断线、报警、急停或条件不安全时不会继续执行动作；
- 模拟模式完成一条成功路径和参数越界、超时、断线三条失败路径；
- 真机验收记录能对应到设备版本、启动图 配置和测试结果。

## 开发约束

- 设备构造阶段不自动连接或执行写操作；
- `connect`、`disconnect`、`status` 等生命周期能力显式定义；
- 动作输入和输出必须能保存为标准 JSON 数据；
- 明确说明超时、取消和重试后的处理方式；重复发送同一请求时，必须说明是否会造成设备重复执行；
- 运动、加热、开门等动作先检查联锁；
- 日志不记录密码、令牌或敏感实验数据。
- 未连接真机或可靠模拟器时，只能标记为静态/模拟验证通过。
